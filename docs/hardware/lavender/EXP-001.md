## Boot Chain

```
PBL (Qualcomm Primary Boot Loader)
  ↓
SBL (Secondary Boot Loader) / XBL
  ↓
ABL (Android Boot Loader) — Little Kernel based
  ↓
boot.img (mmcblk0p60):
  1. Page 0: Android Boot Image v1 header
  2. Page 1+: gzip-compressed ARM64 Linux kernel image
  3. Page 1+: ramdisk
  4. DTBO table with multiple DTB blobs → select by idx
  ↓
Linux kernel entry at EL1
```

## Key Findings

### 1. UART Address — Assumption A-001 REJECTED

**Assumed**: `0x0C1B0000` — WRONG
**Actual**: `0x0C170000` — CONFIRMED (DTB alias `serial0` → `/soc/serial@0c170000`)

Evidence:
- `earlycon=msm_serial_dm,0xc170000` in kernel cmdline
- `/proc/device-tree/aliases/serial0` → `/soc/serial@0c170000`
- Compatible: `qcom,msm-uartdm-v1.4`
- Register range: `0x0C170000-0x0C26FFFF` (size 0x100000)

Impact: The lavender boot stub **must** use `0x0C170000` instead of `0x0C1B0000`.

### 2. Exception Level — Assumption A-008 VERIFIED

**Expected**: EL1
**Evidence**: `CPU: All CPU(s) started at EL1` from dmesg
**Impact**: Our stub entry code must handle EL1 (the current qemu_kernel code already does).

### 3. UART Initialization State — Assumption A-002 PARTIALLY VERIFIED

The bootloader (ABL) initializes the UART for its own debug output. The `earlycon` parameter works without additional initialization by the kernel, confirming the UART is left configured after ABL exits.

However:
- The UART requires `core` and `iface` clocks (from DTB)
- If the clock controller is reset during boot or the stub enters from a different cold boot path, clock init may be needed

**Recommendation**: For M1-B0, attempt to write to UART TX without clock init first. If no output, add clock initialization for gcc (clock-controller@100000).

### 4. MMU State at Entry — Assumption A-009 VERIFIED

The Linux kernel expects the MMU to be disabled at entry (standard ARM64 boot protocol). The kernel enables the MMU itself during early boot.

**Recommendation**: Our stub should start with MMU disabled (as in qemu_kernel).

### 5. Kernel Load Address — Assumption A-003 INCONCLUSIVE

The boot.img header specifies `kernel_load_addr = 0x00008000`. However:
- This may be ignored by ABL, which has its own loading logic
- The actual kernel image is gzip-compressed, so the decompressor stub may handle relocation
- ABL may load the kernel at a fixed platform address

**Required action**: Determine ABL's loading behavior for SDM660. Consider inspecting the kernel image header (decompress gzip to see ARM64 image header with `text_offset`).

### 6. DTB Location — Assumption A-006 VERIFIED

The device uses DTBO (Device Tree Blob Overlay):
- `androidboot.dtb_idx=11` selects DTB #11 from the DTBO table
- `androidboot.dtbo_idx=0` selects DTBO overlay #0
- Separate dtbo partition: `/dev/block/mmcblk0p52`

**Recommendation**: For M1-B0, provide a minimal built-in DTB or hardcode the memory map. DTB parsing can be added later.

### 7. Boot Image Format — Assumption A-005 PARTIALLY VERIFIED

- Format: Android Boot Image **v1** (header version from field at offset 40 = 0x00000001)
- Page size: 4096 bytes
- Kernel: gzip-compressed
- Ramdisk: present
- No vendor_boot partition detected
- Device: mmcblk0p60

## Updated Code: Required Changes

### 1. UART Base Address (MANDATORY)

In `theseus-boot/boot/aarch64/lavender/src/main.rs`:

```rust
// BEFORE (WRONG):
const UART_BASE: *mut u8 = 0x0C1B_0000 as *mut u8;

// AFTER (CORRECT):
const UART_BASE: *mut u8 = 0x0C17_0000 as *mut u8;
```

### 2. Load Address (TO BE VERIFIED)

The linker.ld uses `0x80000000`. The boot.img header says `0x00008000`. These are inconsistent.

**Until ABL behavior is confirmed**, keep `0x80000000` (typical for Qualcomm ARM64) but add a comment noting this is an assumption.

### 3. DTB Handling

For M1-B0, no DTB parsing is needed (hardcoded memory map is sufficient). DTB passing can be added for M1-B1.

## Risks and Open Items

| # | Risk | Impact | Mitigation |
|---|------|--------|------------|
| R1 | ABL may not load kernel at 0x80000000 | Stub won't execute | Determine ABL load address; may need position-independent entry |
| R2 | Boot.img v1 header format may require specific kernel header fields | ABL may reject our stub | Ensure ARM64 kernel image header is present and valid |
| R3 | UART clocks may be gated after bootloader exit | No serial output | Try TX without clocks first; add clock init if needed |
| R4 | Physical UART pins may not be exposed on lavender motherboard | Cannot connect serial cable | Identify UART test points on motherboard |
| R5 | Secure boot may block unsigned images despite orange state | Stub won't boot | Orange state confirmed; should allow booting via `fastboot boot` |
| R6 | Gzip decompression expectation | ABL expects gzip kernel; our stub is raw binary | Package as boot.img without compression (ABL should handle raw images) |
| R7 | Android Boot Image v1 may require valid header SHA | ABL may verify header integrity | Zero SHA may be accepted or ABL may skip verification in orange state |
