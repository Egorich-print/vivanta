## 0. Исходная посылка и главный вывод

**Ни один `kernel_main` Vivanta никогда не выполнялся на физической плате.** Единственная
точка данных по кремнию — EL2-диагностический бинарник RK3568 (реальный вывод по UART,
2026-07-19), который **не линкует ядро**; плата с тех пор наблюдается в **Maskrom**,
загрузка не подтверждена (`docs/hardware/rk3568/README.md:38-41`).

Отсюда следует единственное измерение, которое важнее всего остального в этом документе:

> **Планировать надо по колонке «проверяемо ли без железа».** Железа в контуре нет, поэтому
> блокеры, доказуемые конструкцией (линкер-карта, дизассемблер, архитектурный аргумент,
> юнит-тест на байтах эмитированного образа), — это **дешёвая работа, которую можно закрыть
> сегодня**. Всё, что требует реального MMU-контроллера или реального GIC, — это не
> «задачи», а **лотереи с неизвестным числом попыток**.

### 1.1. Главное числовое уточнение по SB-1

Аудит повторяет цифру «~82 KiB `-O0`-фрейм `kernel_main`»
(`docs/audit/2026-09-24-global-audit.md:67-70`, `STATUS.md:321-326`,
`PLATFORM_BRINGUP.md:239-243`). **Это устаревшее измерение.** INV-003 фиксирует
`sub sp, #0x14000` как пик **до** P0-извлечения гейтов
(`docs/investigations/INV-003-boot-stack-overflow.md:22`, `:55-56`: «измерен 0x14000 → 0xa000
после»).

Переизмерено на текущем HEAD:

```
$ cargo build -p vivanta-target-qemu-aarch64          # профиль dev = -O0
$ rust-objdump -d --disassemble-symbols=_RNv..._14vivanta_kernel11kernel_main \
      target/aarch64-unknown-none/debug/vivanta-target-qemu-aarch64
40237bc4: stp  x29, x30, [sp, #-0x10]!
40237bc8: sub  x9,  sp, #0xa, lsl #12     ; x9 = sp-0xA000 (цель stack-probe)
40237bcc: sub  sp, sp, #0x1, lsl #12      ; цикл, 10 итераций → sp -= 0xA000
40237bdc: sub  sp, sp, #0x810
```

| Величина | Значение | Как получено |
|---|---|---|
| Фрейм `kernel_main` | **43 040 Б = 42,0 KiB** | `0x10 + 0xA000 + 0x810` из пролога |
| Пиковая цепочка прямых `bl` от `kernel_main` | **97 872 Б = 95,6 KiB** (5 кадров) | статический анализ графа вызовов по дизассемблированному графу |
| Пик через любой гейт (`gate_dual_elf` и т.д.) | **95–97 KiB** суммарно | те же гейты — `kernel/src/lib.rs:86,146,198,229,289,336,413,497` |
| `AddressSpace` | 9 792 Б | собственный лог ядра `[SIZE] AS=9792` |
| `VaAllocator::try_new` | 18 624 Б | фрейм |
| `address_space::register` | 19 728 Б | фрейм |
| `sys_fork` | 32 KiB | фрейм; стек потока 64 KiB (`INV-003:74-76`) |

**Следствия:**

1. **16 KiB меньше одного фрейма `kernel_main` в 2,4 раза.** Переполнение происходит в
   прологе (`kernel/src/lib.rs:560` вызывается из `target-x96q/src/main.rs:181`), ещё до
   какой-либо проверки. Для `x96q`/`suma-q5` это не «риск», а гарантия.
2. **Гейты уже вынесены.** Подсказка «вынести код гейтов из `kernel/src/lib.rs`» (2106 строк)
   **уже реализована**: все семь гейтов помечены `#[inline(never)]` и вызываются из
   `kernel/src/lib.rs:1274-1291`. Остаточные 42 KiB — это `-O0`-локалы самого `kernel_main`.
   Значит «сначала вынести гейты» — не план, а уже сделанная работа.
3. **256 KiB = 2,7× к худшей статической цепочке.** Адекватно, но «запас на 2×» в комментарии
   линкера (`target-qemu-aarch64/linker.ld:38-39`) относится к пику **одного** фрейма, а не
   цепочки.

## 2. Разделение работы: (A) проверяемо / (B) нужен кремний / (C) не проверяемо вовсе

### 2.1. Открытие, меняющее категоризацию SB-2/SB-3

`docs/architecture/arm-exception-state.md:139-147` утверждает:

> «QEMU не показывает этот дефект… Это **silicon**-блокер, а не логическая ошибка».

**Это неверно, и это самая дорогая ошибка в бэклоге.** Проверено экспериментально на этой
машине (`clang -target aarch64-none-elf` + `qemu-system-aarch64 -M virt -cpu cortex-a53`):

```asm
_start:
    mrs  x2, CurrentEL ; and x2,#0xC ; lsr x2,#2 ; add w1,w2,#48 ; str w1,[x0]
    mrs  x2, CurrentEL ; and x2,#0xC ; lsr x2,#2 ; add w1,w2,#48 ; str w1,[x0]
    mrs  x3, CPACR_EL1 ; lsr x3,#20 ; and x3,#3  ; add w1,w3,#48 ; str w1,[x0]
    fmov d0, xzr                            // БЕЗ записи в CPACR_EL1
    mov  w1,#70 ; str w1,[x0]               // 'F'
```

Вывод по UART: `110` и **больше ничего**:

```
Taking exception 1 [Undefined Instruction] on CPU 0
...from EL1 to EL1
...with ESR 0x7/0x1fe00000          <-- EC=0b000111 = Trapped SVE/SIMD/FP
...with ELR 0x40200044
```

То есть **QEMU моделирует ловушку FP при `CPACR_EL1.FPEN=0b00` и доставляет её на EL1.**
Три вывода, каждый из которых меняет план:

1. **QEMU в состоянии проверить SB-2.** Ловушка воспроизводится детерминированно.
2. **Причина зелёного гейта — другая.** `qemu-system-aarch64 -M virt -kernel <ELF>` входит на
   **EL1** (измерено: `CurrentEL == 1`, `SPSR 0x400003c5` в `-d int`). Поэтому таргет QEMU
   уходит по **ветке `6:`** (`target-qemu-aarch64/src/main.rs:33-35`) — единственной
   правильной — и **EL2-ветка на QEMU мертва**. Это и есть причина, почему гейт проходит.
3. **EL2-ветку можно покрыть на QEMU принудительно.** Достаточно собрать вариант таргета,
   который не детектирует EL, а безусловно выполняет общий преамбульный путь. Тогда
   неправильный вариант упал бы в ловушку на первой же NEON-инструкции `write_volatile`.

#### Категория (B) — **нужен кремний**

| ID | Что именно нельзя доказать без платы |
|----|--------------------------------------|
| **SB-7a** | Принимает ли реальный Cortex-A55/A53 дескриптор таблицы `0b10` вместо `0b11`. Проект сам измерил, что **QEMU на `0b10` зависает** (`arch-aarch64/Cargo.toml:13-16`) — то есть ровно та конфигурация, на которой можно было бы проверить, специально нерабочая. Это и делает блокер неразрешимым в текущей схеме |
| **SB-B1** | **~~DAIF `#2` вместо `#4`~~ — СНЯТ (2026-09-29).** Прежняя запись утверждала, что `#2` маскирует SError и что с `#4` GIC перестаёт доставлять таймер. Это неверно: `imm4` кодируется bit3=D, bit2=A (SError), bit1=I (IRQ), bit0=F, поэтому `DAIFSet/Clr #2` — корректная IRQ-маска (I), а `PSTATE.I` (бит 7) ею и управляется; `#4` ставит SError-маску (A). Эксперимент с `#4` провалился потому, что `enable()` не снимал IRQ-маску, — дефект эксперимента, а не GIC. **Признаков дефекта доставки IRQ в GIC нет; аппаратного дефекта GIC нет.** Блокер исключён из миссии |
| **SB-B2** | Достижение `kernel_main` и выход в EL0 на любой из плат |
| **SB-B3** | Приём `0x00C00538`/GICv3-кодировок на реальном GIC-400 (Allwinner H313) и на GIC RK3568 |
| **SB-B4** | Восстановление RK3568 из Maskrom (нужен Linux-хост с `rkdeveloptool` либо JTAG через FT232H + OpenOCD — `docs/hardware/rk3568/uboot-emmc-bringup.md:134-158`; **ни то, ни другое не выполнялось**) |

## 3. Дизайн фикса по каждому блокеру

### SB-1 — Boot-стек: реальный фикс, а не «скопировать 262144 в шесть файлов»

**Опция A — расширить стек везде до 256 KiB.**
Файлы: `target-{x96q,suma-q5,rk3568,lavender}/linker.ld` (по одной строке).
Объём: **тривиальный**. Риск регрессии: **нулевой**.
Побочные эффекты, которые надо учесть:
- на `rk3568` и `lavender` это **бессмысленно**: `target-rk3568/Cargo.toml` не зависит от
  `vivanta-kernel` вовсе, а `adapter_main` в `target-lavender/src/main.rs:78-80` уходит в
  `loop{spin_loop()}` и `kernel_main` не зовёт вообще;
- `target-suma-q5/linker.ld:9` — база 0x01080000, образ уже ~4.8 МБ; +240 KiB не проблема;
-   **реальный риск есть на `x96q`**: `__bss_end` = `0x40350930`, `__stack_top` станет
  `0x40390930`. При DRAM-базе 0x40000000 это штатно, но `page_tables_start` вычисляется
  как `kernel_end`, а `kernel_end` — это `__stack_top`
  (`kernel/src/lib.rs:603` → `:614`, `page_tables_size = 0x5000` на `:615`).
  С 16 KiB отступ был 0, с 256 KiB — 240 KiB; надо убедиться, что `memory_discovery` не
  съест этот диапазон (проверяется логом `Managed … ` и `RAM ident:`).

**Опция B — ужать кадр.**
Оговорка из §1.1: гейты уже вынесены. Остаток 42 KiB — `-O0`-локалы `kernel_main`:
`SystemState` (`kernel/src/state/mod.rs:13-18`), `PmmBitmap` (`kernel/src/pmm.rs:7-12`),
`PmmBackend`, локаль `available`, плюс все temporaries по значению при `-O0`
(`AddressSpace` — 9 792 Б, `VaAllocator`, `MemoryMap`).
Правильный ход — **убрать бут-состояние из кадра целиком**, а не «ещё немного разнести»:

```rust
// kernel/src/lib.rs — новое
struct BootState {
    system_state: SystemState,
    pmm: pmm::PmmBitmap,
    pmm_backend: PmmBackend,
}
static mut BOOT_STATE: MaybeUninit<BootState> = MaybeUninit::uninit();
// kernel_main держит ровно один указатель
```
(либо `Box<BootState>` на kernel-heap, но он инициализируется в середине `kernel_main`, так что
`static MaybeUninit` + локальный `&'static mut` безопаснее).

Измеренный эффект: фрейм `kernel_main` **42,0 KiB → ~200 Б**.
Новая худшая статическая цепочка: `gate_fault_oom(448) → register(19 728) →
AddressSpace::new(16 032) → VaAllocator::try_new(18 624)` = **55,6 KiB**.
То есть 64 KiB на бут-стек хватило бы — **впритык**, и `sys_fork` (32 KiB на стеке потока
в 64 KiB, `INV-003:74-76`) остался бы тем же классом риска.
Объём: **средний** — переписывание бут-секции `kernel/src/lib.rs:560-745` плюс все
`&mut`-передачи в гейты (`:1274-1291`). Риск: **средний** — трогается весь путь загрузки.

| | A (расширить) | B (ужать) | A + B |
|---|---|---|---|
| Объём | тривиальный | средний | средний |
| Риск | нулевой | средний | средний |
| Снимает «tripwire»? | **нет** — кадр продолжает расти с каждым новым гейтом | **да** — кадр перестаёт зависеть от гейтов | да |
| Чинит стеки потоков? | нет | частично (только если применить к `fork`) | частично |
| Требует железа для проверки? | нет | нет | нет |

**Рекомендация: A немедленно (разблокирует `x96q`), B как основной фикс.**
Плюс третьим, обязательным элементом — **сделать tripwire машинным**. Сейчас он держится на
комментарии в линкер-скрипте (`target-qemu-aarch64/linker.ld:35-40`,
`target-rpi3b-plus/linker.ld:34-35`), а в `x96q`/`suma-q5`/`rk3568`/`lavender` комментария
нет вообще — именно поэтому раскол и возник и просуществовал. Нужен `tools/stack-audit.sh`:
собрать шесть таргетов, распарсить прологи `rust-objdump`, просуммировать статическую цепочку
и упасть при превышении 50 % объявленного бюджета. Это переводит целый класс дефектов из
«заметят на плате» в «упадёт в CI».

**Дополнительно:** `src/main.rs` таргетов несут ещё одну стоякую проблему —
`target-lavender/linker.ld` **не имеет секций PHDRS**, а `.text` без явного `ALIGN`
(`:6`) при `KEEP(*(.text._start))` не гарантирует 16-байтовое выравнивание точки входа;
ARM64-Image требует 4-байтового выравнивания как минимум, но заголовок U-Boot ожидает
64-байтную структуру. Это вне заявленного бэклога, но относится к тому же файлу.

### SB-2 — FP/SIMD

Фикс **одинаков на всех шести таргетах** и не зависит от EL:

```asm
msr  daifset, #0xf
msr  CPTR_EL2, xzr          // TFP = 0: ловушки FP не маршрутизируются на EL2
msr  CPACR_EL1, xzr          // обнулить остальные поля
mov  x5, #(0b11 << 20)      // FPEN = 0b11
msr  CPACR_EL1, x5           // FP разрешён на EL1 и EL0
isb
```

Ключевое архитектурное решение — **отказаться от ветвления по `CurrentEL` для FP**.
`CPTR_EL2` и `CPACR_EL1` доступны для записи и с EL2, и с EL1, поэтому обе записи
безусловны. Побочный выигрыш: **устраняется целый класс расхождений** — сегодня `rpi3b`
на EL2 делает no-op и при этом **не содержит `msr CPACR_EL1` вообще**, то есть у него нет
второго пути, на который можно было бы опереться.

**Про `msr CPACR_EL1` с EL2.** Это допустимо: `target-rk3568/src/main.rs:191` делает
именно это на реальном Cortex-A55 и отработал (`docs/hardware/rk3568/board-info.md:392-394`,
маркер `C3` = FPEN=3 в расшифровке на `:409-437`). Доказательство есть.

**Риск.** Единственный реальный риск — **регрессия в QEMU**: если кто-то когда-нибудь
вернёт `CPTR_EL2` к установке бита, QEMU этого не заметит (нет EL2-пути). Поэтому «золотой»
байтовый тест обязателен (§4.4). Второй риск: `msr CPACR_EL1, xzr` обнуляет и другие поля
`CPACR_EL1` (в т.ч. `SVEEN[31:30]`), что на сброшенном кремнии безопасно — и точно так же
делает эталон `target-rk3568/src/main.rs:191`.

**Объём:** маленький. Пять правок по ~5 строк + обязательный тест.

### SB-3 — EL0 FP/SIMD-контекст

Два независимых места, и оба надо закрыть:

1. **`eret_to_user_stub`** (`arch-aarch64/src/user.rs:18-…`) — точка возврата в EL0. Сейчас
   восстанавливает `x0-x30` (`:34-47`) и системные регистры из `ExceptionFrame`.
2. **`save_and_eret_sync`** (`arch-aarch64/src/vectors.rs:136-…`) и `save_and_eret`
   (`:80-…`) — сохранение на входе.

Дизайн: расширить `ExceptionFrame` полями `d8-d15` (8×8 Б), `fpsr`, `fpcr`; в
`save_and_eret_sync` добавить `stp d8,d9,[sp,#..]` … `stp d14,d15`, `mrs fpsr`, `mrs fpcr`;
в `eret_to_user_stub` — обратные `ldp`/`msr`. `x0-x7` ( volatile-банк, caller-saved по ABI)
сохранять не нужно: по AAPCS64 это банк, который не обязан переживать вызов.

**Это ломает два статических утверждения**, которые надо обновить в том же коммите:
`arch-aarch64/src/context.rs:23` (`size_of::<ExceptionFrame>() == 34 * 8`) и
`arch-aarch64/src/user.rs:11` (комментарий «272»). И `context_fork`
(`context.rs:185`) копирует кадр целиком — с расширением это останется корректным.

**Риск:** средний. Кадр растёт с 272 до 376 Б; `context.rs:118` размещает синтетический кадр
в `stack_top - FRAME_SIZE`, поэтому `FRAME_SIZE` пересчитается автоматически, но
выравнивание надо проверить. Порядок обязателен: **сначала SB-2** (иначе `CPACR_EL1.FPEN=0`
и `d8-d15` недоступны на EL0 и сохранять нечего — код будет unreachable).

**Проверяемость:** тест на EL0 под QEMU — пользовательский код пишет в `d8-d15`/`FPSR`/`FPCR`,
уступает планирование, проверяет после возврата. Работает, потому что ловушка FP на QEMU
моделируется (§2.1), а EL0-потоки ядро уже гоняет.

### SB-4 — `execve` и I-cache

Фикс: `load_elf` уже возвращает образ; нужно вернуть из него диапазон PT_LOAD с
`PF_X` и заменить `kernel/src/syscall/process.rs:638` на
`mmu_flush_icache_range(exec_va_start, exec_va_end - exec_va_start)`.
`flush_icache_range` (`arch-aarch64/src/mmu.rs:712-731`) уже умеет обходить диапазон
с выравниванием по `ctr_el0` — менять ничего не нужно.

**Риск:** низкий, но есть тонкость — после `unmap_all` (`process.rs:612-614`) старые
трансляции сняты; обновлять I-cache нужно **по VA нового образа в активном AS**, что
комментарий на `process.rs:634-637` уже утверждает и что верно. Объём: маленький-средний
(нужно прокинуть диапазон из `exec::load_elf`).

### SB-5 — Валидация FDT

Три меры:

1. **Единый валидатор** `FdtScanner::validate(ptr) -> Result<(u32 /*totalsize*/, ...)>`,
   проверяющий `null`, `magic == 0xD00DFEED`, `version >= 16`, `off_dt_struct`/`off_dt_strings`/
   `size_dt_struct` **внутри `[hdr, hdr+totalsize)`**. Вызывать из `console()`,
   `cpu_count()`, `interrupt_controller()` — они сейчас читают заголовок без проверок
   (`fdt.rs:236-238`, `:677-679`, `:770-772`).
2. **`totalsize` как граница**, а не как печатное поле. Сейчас `:54` и `:460` читают его и
   больше нигде не используют; `struct_end` считается от `off_dt_struct + size_dt_struct`
   (`:241`, `:464`) без всякой проверки.
3. **`report()` тоже должен проверять `version`** — сейчас проверка есть только в `probe()`
   (`fdt.rs:65`).

Документированный fallback «без DTB» действителен только в `x96q`
(`platform-allwinner-h616/src/lib.rs:56-62` — при отсутствии console-узла печатает в
захардкоженный NS16550). Но и он вызывает `FdtScanner::console(dtb_addr)` **до** проверки,
а `platform-qemu/src/lib.rs:63` вообще делает `.expect("no console in FDT")` — то есть
документированный путь не работает ни на одной плате. Объём: маленький. Риск: низкий.

### SB-6 — BSS-обнуление

Один цикл на пять таргетов, заменяемый на корректный по хвосту:

```asm
1:  cmp  x3, #8
    b.lo 3f
    str  x2, [x1], #8
    sub  x3, x3, #8
    b    1b
3:  cbz  x3, 2f
    strb wzr, [x1], #1
    sub  x3, x3, #1
    b    3b
2:
```
Плюс проверка, что `__bss_end` не заходит за `__stack_bottom`. Объём: маленький.
Замечание: сейчас дефект **латентный** — измеренные размеры BSS кратны 8, а `__bss_end`
попадает в 8-байтный паддинг `ALIGN(16)` (`__bss_end = 0x402d0528`,
`__stack_bottom = 0x402d0530` на QEMU), то есть до ≤7 байт в стек. Это не «не работает»,
это «работает случайно».

### SB-7b — Окно GIC на `suma-q5`

Расширить `MMIO_REGIONS` (`target-suma-q5/src/main.rs:139-142`) так, чтобы окно покрывало
`0xc430_1000` (дистрибьютор) и `0xc430_2000` (CPU-интерфейс): либо база `0xc430_0000`,
размер `0x3000`. `x96q` в порядке: `0x03000000/0x20000` покрывает и `0x03000000`, и
`0x03010000`. Плюс хост-утверждение по всем парам «регион GIC ⊂ объединение MMIO» —
чтобы класс дефекта не вернулся на шестом таргете.

### SB-7c — Консоль `suma-q5`

Драйвер Meson UART не существует (`platform-amlogic/src/lib.rs:106` — единственный `TODO`
в дереве). Это **разработка драйвера**, а не шаг bring-up, и она стоит дороже, чем весь
остальной список. Рекомендация в §5: **заморозить таргет**, а не чинить.
Но общее упрочнение из SB-9 (`with_console` не паникует, а деградирует в raw-UART по
`debug_uart_base()` — `boot_common/src/lib.rs:108`) стоит сделать везде: оно превращает
целый класс молчаливых зависаний в видимый отказ.

### SB-10 — Консолидация скриптов прошивки

Канон — `docs/hardware/rk3568/scripts/flash-serial-mm.py`: 1 500 000 бод
(`:37`), `mm.l` (`:65`), `CHUNK = 64` (`:27`), `WORD_DELAY = 0.06` (`:28`),
`CHUNK_START/END` (`:29-30`). `vivanta-boot/flash_rk3568.py` — дубль, который:
115200 бод (`:13`), `mw.l` построчно с 5 мс (`:125`, `:144`), плюс **генерирует свой собственный
минимальный DTB** (`:18-85`) с `compatible = "linux,dummy-virt"` (`:46`) — то есть на реальной
плате сканер FDT получает нечто, не соответствующее RK3568.

Предложение:
1. Удалить `vivanta-boot/flash_rk3568.py` как источник истины; оставить один скрипт.
2. Перенести его в `docs/hardware/rk3568/scripts/` (рядом с каноническим) — он загружает
   произвольный образ по произвольному адресу, то есть переиспользуем и для `u-boot.itb`.
3. `build.sh` уже указывает на него в трёх местах — заменить на канонический путь.
4. Отдельно: минимальный DTB в скрипте — плохая идея для валидации. На RK3568 DTB должен
   приходить из U-Boot (`${fdt_addr_r}`), как в команде x96q
   (`build.sh`, ветка `x96q`: `booti 0x40280000 - ${fdt_addr_r}`). Синтетический DTB годен
   только для отладки загрузчика и должен быть помечен как таковой.

Объём: маленький. Риск: нулевой (старый скрипт не воспроизводим на текущем baud).

## 4. Дедупликация преамбулы: единый источник, который нельзя расщепить

### 4.1. Что дублируется сейчас

Шесть `target-*/src/main.rs` содержат практически одну и ту же ~40-строчную преамбулу
(`core::arch::global_asm!`): чтение `CurrentEL`, «включение FP/SIMD», установка `SP`,
обнуление BSS, переход в Rust. Evolution plan это уже зафиксировал:
`docs/architecture/evolution-plan.md:296` («Entry code duplicated… Should be in a shared
`boot/arch/aarch64/entry.S`»), `:329-333`, `:484`, `:531`, `:608`. Дублирование — не
косметика: **именно оно и произвело SB-2** (пять копий, пять одинаковых ошибок, одна
«правильная», и та — у таргета, который не линкует ядро).

### 4.2. Почему полная дедупликация «в лоб» невозможна — и как это обойти

Преамбулы **действительно различаются**, и это не шум:

| Отличие | Где |
|---------|-----|
| Заголовок ARM64 Image: `text_offset` 0 / 0x80000 / 0x00280000 / `image_size` 0x400000 | `x96q:32-33`, `suma-q5:39-40`, `rpi3b:24-26`, `lavender:18-19`, `rk3568:21-26` |
| Переход EL2→EL1 (`HCR_EL2.RW`, `SPSR_EL2`, `eret`) — есть/нет | `x96q:57-65`, `rpi3b:43-51`; **нет** в `suma-q5`, `lavender`, `qemu` |
| Сохранение `x0` (DTB) в `BOOT_CONTEXT` | `x96q:88-90`, `suma-q5:84-86`, `rpi3b:67-69`; **нет** в `qemu`, `lavender`, `rk3568` |
| Обнуление BSS — в ассемблере или в Rust | в ассемблере у пяти; в Rust — `rk3568:195-206` |
| Специфика загрузчика: `ldr x1, =0x09000000` + проверка магии `0xEDFE0DD0` | только `qemu:49-58` |
| Дополнительный `.fill` до 0x80000 | только `lavender:26` |
| `ldr x1, =__stack_top` (literal pool) vs `adrp/add` | `qemu:37` против остальных |

Отсюда **правильная форма**: не «один файл на шесть», а **одно ядро + явные точки
расширения**.

### 4.3. Механизм

Rust-эквивалент `include!` для ассемблера — `include_str!` внутри `global_asm!`
(`global_asm!` принимает `concat!`/`include_str!`, это разворачивается до `llvm_asm!`;
путь резолвится **относительно исходника**, то есть от `$CARGO_MANIFEST_DIR` таргета, и
не зависит ни от cwd, ни от `.cargo/config.toml`).

Предлагаемая раскладка:

```
vivanta-boot/boot_common/src/entry_arm64.S     ← ЕДИНСТВЕННАЯ копия общей части
vivanta-boot/target-<x>/src/main.rs            ← только заголовок + хуки
```

`entry_arm64.S` содержит **ровно** то, что обязано быть одинаковым, и ничего больше:

```asm
/* vivanta-boot/boot_common/src/entry_arm64.S
   Общая часть преамбулы AArch64. Единственная копия в дереве.
   Вставляется в target-*/src/main.rs через
   global_asm!(concat!(include_str!(<per-target prefix>),
                       include_str!("../boot_common/src/entry_arm64.S"))) */

    .macro VIVANTA_ENABLE_FP
        /* Выполняется БЕЗ ветвления по EL: оба регистра доступны
           для записи и с EL2, и с EL1. Порядок фиксирован. */
        msr  CPTR_EL2, xzr        /* TFP = 0  */
        msr  CPACR_EL1, xzr
        mov  x5, #(0b11 << 20)    /* FPEN = 0b11 */
        msr  CPACR_EL1, x5
        isb
    .endm

    .macro VIVANTA_SET_STACK
        adrp x1, __stack_top
        add  x1, x1, :lo12:__stack_top
        mov  sp, x1
    .endm

    .macro VIVANTA_ZERO_BSS
        /* хвост по байтам — см. SB-6 */
        adrp x1, __bss_start
        add  x1, x1, :lo12:__bss_start
        adrp x2, __bss_end
        add  x2, x2, :lo12:__bss_end
        sub  x3, x2, x1
        cbz  x3, 9999f
        mov  x2, xzr
1:      cmp  x3, #8
        b.lo 2f
        str  x2, [x1], #8
        sub  x3, x3, #8
        b    1b
2:      cbz  x3, 9999f
        strb wzr, [x1], #1
        sub  x3, x3, #1
        b    2f
9999:
    .endm
```

Что это даёт против шести копий:

- **SB-2 становится структурно невозможен.** Нет ветки «EL2 против EL1» — нет места,
  где можно написать не тот регистр; нет метки, которую можно проскочить. `VIVANTA_ENABLE_FP`
  — безусловная, из одного места.
- **SB-6 чинится один раз**, а не в пяти копиях.
- **Путь `SP` одинаков** у всех, кроме `qemu` (literal pool), и это сознательное
  исключение, оформленное как переопление макроса.

### 4.4. Что делает расщепление невозможным **механически**, а не «по договорённости»

Комментарий в `.S` — это не гарантия. Гарантия — **тест на байтах эмитированного образа**.

Собранная каноническая последовательность (проверено: `clang -target aarch64-none-elf`
+ `rust-objcopy -O binary --only-section=.text`):

```
+00: df4f03d5   msr  daifset, #0xf
+04: 5f111cd5   msr  CPTR_EL2, xzr          <- TFP = 0
+08: 5f1018d5   msr  CPACR_EL1, xzr
+0c: 0506a0d2   mov  x5, #0x300, lsl #16    <- 0b11 << 20
+10: 451018d5   msr  CPACR_EL1, x5          <- FPEN = 0b11
+14: df3f03d5   msr  daifset, #0xf
+18: 1f2003d5   isb
```

**Золотое окно преамбулы** (24 байта):
`5f111cd55f1018d50506a0d2451018d5df3f03d51f2003d5`

`tools/entry-golden.sh` для каждого из шести таргетов:
1. `cargo build -p <target>`;
2. взять адрес `_start` из таблицы символов;
3. `rust-objcopy -O binary --only-section=.text`, вырезать 24 байта со смещения, равного
   `(_start - <начало .text>) + <смещение до FP-последовательности>`;
4. `cmp` с золотой строкой; расхождение → падение.

Смещение до FP-последовательности **вычисляется из символов**, а не захардкожено: это
означает, что тест переживает изменение длины ARM64-Image-заголовка. Альтернативно —
искать в дизассемблерном выводе `msr CPTR_EL2` и брать следующие 6 инструкций.

Второй, независимый тест — **FPEN-readback в самом коде**, а не только в тесте:
одна строка в адаптере каждого таргета

```rust
let fpen = { let v: u64; core::arch::asm!("mrs {}, cpacr_el1", out(reg) v); (v >> 20) & 3 };
println!("  FPEN={} CPTR_EL2.TFP={}", fpen, /* ... */);
```

печатает по UART то, что читает `docs/architecture/arm-exception-state.md:80-87`.
На QEMU это напечатает `FPEN=3` (ветка `6:`), и на любой реальной плате — то же самое,
если EL2-путь починен. Это дешёвый, постоянно работающий детектор регрессии, который не
зависит от CI.

### 4.5. Чего дедупликация **не** решает

- `spec-table-desc` — фича Cargo, а не ассемблера; дедупликация на неё не влияет.
- `PAHRS`-подобные per-target параметры заголовка — их придётся оставить в per-target
  префиксе. Это осознанно: заголовок ARM64 Image — это **контракт с загрузчиком**, и
  ошибиться в нём нельзя. Дублирование в пяти местах приемлемо **именно потому**, что
  это данные, а не логика.
- Per-target `.cargo/config.toml` (SB-8) остаются мёртвым мусором и должны быть удалены,
  а не «починены»: их содержимое дублирует `build.rs` (`-T .../linker.ld`) и, будучи
  прочитанным, **сломало бы линковку** дублированным `-T`.

### 5.2. Рекомендация по железу

**Продолжать на RPi 3B+. RK3568 — не партисипировать, а отложить.**

Аргументы:

1. **Разница между «итерация» и «расходятся на инструментах».** На RPi цикл —
   `build.sh rpi3bp` → `dd` на SD → читать USB-TTL. Восстановление SD-карты занимает секунды,
   риск нулевой. На RK3568 следующий шаг требует **Linux-хоста с USB-passthrough либо
   пайки FT232H к предположительным площадкам** (`uboot-emmc-bringup.md:144`: «TP1/TP4
   near U28/R452 are the **likely** JTAG pads»). Ни то, ни другое не выполнялось. Это
   означает: следующий цикл на RK3568 будет циклом по инструментам, а не по Vivanta —
   а весь смысл перехода на кремний в том, чтобы получать данные о Vivanta.
2. **RPi — единственная плата, где цель уже в коде.** `kernel_main` вызывается
   (`target-rpi3b-plus/src/main.rs:132`), ядро линкуется, `spec-table-desc` включён —
   то есть на ней **немедленно** проверяется SB-7a, который на RK3568 не проверяется вовсе
   (у rk3568 нет зависимости от `vivanta-arch-aarch64`).
3. **Первый блокер, который убьёт загрузку на RPi, — ровно тот, который мы уже умеем
   чинить с высокой уверенностью.** SB-2 — это тихий завис в ловушке FP. Он
   воспроизводится на QEMU (§2.1), он чинится пятью инструкциями, он проверяется
   «золотым» байтовым тестом и FPEN-readback'ом. Ровно тот класс работы, который даёт
   результат без железа.
4. **Ограничение RPi честно и не блокирует первый рубеж.** Нет GIC ⇒ `interrupt_controller:
   None` (`target-rpi3b-plus/src/main.rs:127`) ⇒ только кооперативный планировщик, гейт G4
   печатает SKIP (`PLATFORM_BRINGUP.md:179`, `:248-249`). Это мешает на **втором** рубеже
   (вытеснение), а не на первом («дошёл до `kernel_main`, напечатал баннер»). Достижение
   первого рубежа — достаточная цель для выбора платы.
5. **RK3568 при этом не выбрасывается.** Он нужен позже, и он нужен именно как вторая
   плата: GIC есть, `CPTR_EL2`/`CPACR_EL1` на реальном Cortex-A55 **уже доказали** работу
   фикса SB-2 (`board-info.md:419`, маркер `C3`). Параллельно с работой над RPi дёшево
   снять один вопрос: `rkdeveloptool ld` на macOS подтверждает, что BootROM-USB-путь жив.
   Это один запуск команды и он не требует ни Linux, ни пайки.

**QEMU — не замена железу, но главный инструмент верификации.** Из шести таргетов QEMU
покрывает один, и в конфигурации, где EL2-ветка мёртвая. Отсюда прямое следствие для
плана: **обязательно добавить принудительный EL2-режим под QEMU** — иначе самый
серьёзный блокер останется непроверяемым до следующего похода в железу.

**Порядок по платам:** RPi 3B+ и X96Q — параллельно (разные таргеты, общий фикс
преамбулы даёт обоим). suma-q5 и lavender — заморозить и убрать из активного роадмапа,
чтобы они перестали выглядеть как «ещё не доведённые», и перестали размывать внимание.
AIBOX — оставить в режиме исследования.

| `boot_common/src/fdt.rs` | SB-5 — один автор |
| `arch-aarch64/src/context.rs` + `user.rs` + `vectors.rs` | SB-3 — один автор |

| `kernel/src/syscall/process.rs` | SB-4 — один автор |

### 6.2. Что можно делать одновременно

**Параллельно, без конфликтов (4 агента):**

- **A1** — SB-5 (FDT-валидация): `boot_common/src/fdt.rs` + хост-тесты. Не касается
  `main.rs`, не касается ядра.
- **A2** — SB-10 (консолидация `flash_rk3568.py`): изолированный файл.
- **A3** — SB-7b (окно GIC на suma-q5): **только если сумa-q5 не замораживается** —
  иначе вместе с A4 в одну задачу.
- **A4** — `tools/stack-audit.sh` + `tools/entry-golden.sh`: новые файлы, ноль конфликтов.

**Параллельно, но с явной точкой сериализации:**

- **A5** — §4 (создание `boot_common/src/entry_arm64.S` + **один** пилотный таргет).
  Пилотом должен быть **`target-rk3568`**: он единственный не линкует ядро, поэтому
  не может сломать гейт, и при этом содержит корректную FP-последовательность —
  идеальный донор.
- **A6** — SB-3 (EL0 FP-контекст): `arch-aarch64/src/{context,user,vectors}.rs` +
  `arch-api`. **Строго после SB-2** (иначе сохранять нечего), но **может идти параллельно
  с §4**, поскольку файлы не пересекаются: преамбула — `main.rs`, контекст — `arch-aarch64`.
  Единственное пересечение — `ExceptionFrame`, которого правка преамбулы не касается.
- **A7** — SB-4 (execve icache): `kernel/src/syscall/process.rs` + `exec/`. Не пересекается
  ни с чем.

### 6.3. Точки сериализации (жёсткий порядок)

1. **`kernel_main` / преамбула.** SB-1 (опция A), SB-2, SB-6 и §4 дедупликация **все**
   правят одни и те же файлы. Правильная последовательность внутри одного потока работ:
   1. A5-пилот на `target-rk3568` → закоммитить `entry_arm64.S` и `entry-golden.sh`;
   2. мигрировать остальные пять `main.rs` **одним коммитом** (иначе промежуточное
      состояние смешивает старую и новую преамбулу);
   3. в этом же коммите — SB-2 (FP) и SB-6 (BSS-хвост): они становятся правками
      самого `.S`, а не шести копий;
   4. затем SB-1 опция A — четыре `linker.ld` одним коммитом (тривиально, отдельный,
      чтобы его можно было откатить не трогая остальное).
2. **SB-1 опция B** (`BootState` в `kernel/src/lib.rs`) — **строго после** всех
   boot-гейтов, потому что он переписывает весь путь загрузки `kernel/src/lib.rs:560-745`.
   Должен идти **последним** среди правок ядра, иначе конфликтует с любым ещё не
   завершённым изменением бут-секции.
3. **SB-3 после SB-2.** Обосновано выше.
4. **`spec-table-desc` для сумa-q5/x96q** — только если таргет разморожен; это изменение
   `Cargo.toml` с риском унификации фич, поэтому оно **не должно** попадать в один коммит
   ни с чем-либо ещё (`PLATFORM_BRINGUP.md:229-233` — предупреждение об унификации).

### 6.4. Ответ на исходный вопрос: что чинится и проверяется **сегодня, без железа**

| | Блокеры | Как проверяется |
|---|---|---|
| **Чинится и проверяется сегодня** | SB-1 (опция A), SB-2, SB-4, SB-5, SB-6, SB-7b, SB-7d, SB-9, SB-10, §4 целиком, SB-3 | линкер-карта, дизассемблер, «золотые» байты, хост-тесты, QEMU (включая принудительный EL2) |
| **Требует платы** | SB-7a, первый `kernel_main`, восстановление RK3568 (SB-B1 снят 2026-09-29) | — |
| **Не проверяемо вовсе** | SB-7a, SB-B2 | §2.2 категория (C): прокси указаны, и ни один из них не является доказательством |

**Главное следствие для миссии:** из десяти заявленных блокеров **восемь закрываются
сегодня, полностью проверяемо, без единого входа в железа**. Оставшийся
(`spec-table-desc`) — принципиально неразрешим в текущей схеме, и это
свойство схемы, а не небрежность плана. (`SB-B1`/DAIF/GIC исключён: IRQ-маска
`#2` корректна, дефекта доставки в GIC нет — поправка 2026-09-29.) Если после
закрытия восьми переход EL2→EL1,
`kernel_main` и всё остальное работает на QEMU, то у RK3568 останется ровно
**один** известный вопрос вместо десяти, и он будет известен заранее.

## 7. Оценка объёма (относительная, без календаря)

| Работа | Объём | Обоснование |
|---|---|---|
| SB-1 опция A | **тривиальный** | 4 строки в 4 файлах; проверка — линкер-карта |
| SB-1 опция B | **средний** | перенос ~300 строк бут-секции `kernel/src/lib.rs` за один указатель; затрагивает все гейты |
| SB-2 | **малый** | ~5 инструкций × 5 файлов + золотой тест |
| SB-3 | **средний** | 3 asm-макроса + `ExceptionFrame` + 2 статических утверждения; ломает ABI кадра |
| SB-4 | **малый–средний** | прокинуть диапазон из `load_elf`; сама функция обслуживания уже готова |
| SB-5 | **малый** | один валидатор + три вызова + хост-тесты |
| SB-6 | **малый** | один цикл, заменяемый один раз |
| SB-7b | **тривиальный** | 2 числа в массиве |
| SB-7c (Meson UART) | **большой** | новый драйвер UART для нестандартного IP; рекомендация — не делать |
| SB-9 | **малый** | один guard в `with_console` |
| SB-10 | **тривиальный** | удалить дубль, поправить `build.sh` |
| §4 дедупликация | **средний** | новый `.S` + миграция шести файлов + золотой тест; механически устраняет SB-2 и SB-6 |
| `stack-audit.sh` / `entry-golden.sh` | **малый** | скрипты поверх существующих `rust-objdump` / `rust-objcopy` |

## 8. Что было проверено и как (воспроизводимость)

Все числа в §1.1 и §2.1 получены на текущем дереве (`HEAD 273f9bc`, toolchain 1.98.0,
`rust-toolchain.toml`):

```
$ cd vivanta-boot
$ cargo build -p vivanta-target-qemu-aarch64
$ rust-objdump -d --disassemble-symbols=_RNvCs9TZyOdDYZIm_14vivanta_kernel11kernel_main \
      target/aarch64-unknown-none/debug/vivanta-target-qemu-aarch64
$ rust-nm target/aarch64-unknown-none/debug/vivanta-target-<x> | grep -E '__bss|__stack'
```

Эксперимент по ловушке FP (§2.1) — отдельная минимальная программа, собранная
`clang -target aarch64-none-elf` и запущенная под
`qemu-system-aarch64 -M virt -cpu cortex-a53 -d int`; ESR `0x7/0x1fe00000` (EC=0b000111).

Метки уверенности:

- **CONFIRMED** — прочитано в коде по указанным `path:line` либо измерено на артефакте.
- **INFERRED** — выведено из измерения плюс архитектурного правила (например, переполнение
  16 KiB стека на `x96q`: кадр 42 KiB измерен, стек 16 KiB прочитан из линкер-скрипта).
- **UNCERTAIN** — помечено явно. К таковым относятся: (1) применимость `-M sbsa-ref` как
  прокси (модель требует других CPU, проверено отказом); (2) поведение `-M raspi3b` под
  AArch64-образом (модель существует, вывод получить не удалось — **требует отдельной
  проверки, не является основанием для плана**); (3) прием `0b10` реальным ARM (не
  проверяемо); (4) ~~поведение GIC при `DAIFSet #4` на кремнии~~ (снято 2026-09-29:
  `#2` — корректная IRQ-маска, дефекта доставки нет; см. SB-B1).

Никакое утверждение в этом документе не основано на непроверенном «работает на железе».
Единственный артефакт, который **есть** в дереве как доказательство работы на кремнии, —
расшифрованная UART-строка RK3568 от 2026-07-19
(`docs/hardware/rk3568/board-info.md:409-437`), и она относится к EL2-диагностике, **не**
доходящей до `kernel_main`.
