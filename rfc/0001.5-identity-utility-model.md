# RFC-001.5: Identity Utility Model

**Status:** Draft for discussion
**Area:** Core Architecture
**Requires:** RFC-001 (Identity Model)
**Depends on RFCs:** RFC-001
**Supersedes:** Nothing
**Authors:** Theseus Architecture Team

---

## 1. Problem

RFC-001 defines a mechanism for persistent cryptographic identity. But the user's question is correct:

> "What system capabilities actually require persistent identity?"

If the answer is "none," then the identity model is architectural over-engineering. If the answer is "some," we need to know which ones — and whether they justify the complexity.

This document enumerates every capability that identity enables, evaluates whether identity is truly required or merely convenient, and determines the minimum viable identity model.

---

## 2. Identity-Enabled Capabilities

### C1: Architecture-Independent System Migration

**Scenario:**
A Xiaomi Redmi Note 7 user replaces the motherboard with an ARM64-based board that has a different SoC. The original storage is connected to the new board. The system boots on the new hardware.

**With identity:**
The State Chain shows the complete hardware evolution. The system recognizes itself as Theseus-001 at state S7 (CPU replaced), continues booting, and preserves the user environment.

**Without identity:**
The system detects new hardware. It may boot (if drivers exist) but cannot distinguish between "this is the same system with a new CPU" and "this is a different machine that happens to have my storage." Any license keys, trust relationships, or device-specific configurations must be re-established.

**Identity required?** ✅ Yes. Without identity, migration is indistinguishable from first boot.

---

### C2: Storage Replacement Without Reinstallation

**Scenario:**
The eMMC storage on the Xiaomi Redmi Note 7 wears out. The user replaces it with an NVMe module via an adapter. The user environment was backed up on a separate partition. After replacement, the system detects the new storage, finds the user data, and resumes.

**With identity:**
The system knows it is the same entity. It can verify that the data on the new storage is signed by its own identity. It recognizes the replacement as a planned configuration change.

**Without identity:**
The system boots from the new storage. It has no way to verify it is "the same system." From a trust perspective, it is a fresh install that happens to have old data available.

**Identity required?** ✅ Yes. The system needs identity to claim "this is my data" across storage changes.

---

### C3: Hot Hardware Replacement

**Scenario:**
A failed display module is replaced while the system is running. The OS detects the new display, loads the appropriate driver, and reconfigures the graphics stack without rebooting.

**With identity:**
The State Chain records the display change. The system knows it is the same entity, just with a different display.

**Without identity:**
The system detects a new display and loads the driver. Identity is not involved in this detection or driver loading process.

**Identity required?** ❌ No. Hotplug hardware detection and driver loading are standard OS capabilities that do not require system identity. The display replacement is a hardware event, not an identity event.

---

### C4: Clone/Fork Detection

**Scenario:**
An attacker gains physical access to the device, clones the storage, and boots the clone on identical hardware. Both the original and the clone believe they are "the same system."

**With identity:**
Both systems share the same Root Keypair. When their State Chains diverge (the first different State Document), both systems can detect the fork. The original can detect that a clone exists.

**Without identity:**
The cloned system is functionally identical. There is no mechanism to detect the clone. Both systems operate independently without knowledge of each other.

**Identity required?** ✅ Yes. Fork detection is impossible without a shared reference point (the Root Keypair) and divergence detection (the State Chain).

---

### C5: Secure Ownership Transfer

**Scenario:**
The user sells the device to another person. The new owner needs to be recognized as the legitimate controller of the system.

**With identity:**
The original owner signs an Ownership Transfer document using their identity key. The system's Root Keypair remains unchanged. The new owner becomes the recorded owner while the system retains its history.

**Without identity:**
The new owner performs a factory reset. All history is lost. The system becomes a "new" system with no connection to its past. The previous owner retains no verifiable transfer record.

**Identity required?** ✅ Yes. Ownership transfer without identity is just factory reset — history is destroyed.

---

### C6: Multi-Device Identity

**Scenario:**
A user has a phone running Theseus and later buys a tablet also running Theseus. Both devices should share a trust relationship and recognize each other.

**With identity:**
Each device has its own Root Keypair. They establish mutual trust by exchanging identity statements signed by the user's ownership key. Each device knows "I have a sibling."

**Without identity:**
Each device is isolated. There is no mechanism for devices to establish a verifiable relationship. Any trust must be configured manually (SSH keys, account login, etc.).

**Identity required?** ✅ Yes. Device-to-device trust relationships require verifiable identities on each side.

---

### C7: Autonomous Agent Continuity

**Scenario:**
An AI agent runs on the Theseus system. The agent has learned user preferences, established trust relationships with remote services, and accumulated state. The hardware fails. The agent is migrated to new hardware.

**With identity:**
The agent can verify that it is running on the "same system" (same Root Keypair, same State Chain). It can present proof of continuity to remote services: "I am the same agent that was previously at IP address X, running on hardware configuration Y."

**Without identity:**
The agent is a set of files on storage. It can be copied to new hardware, but it cannot prove its continuity to any external service. Service trust relationships are broken.

**Identity required?** ✅ Yes. Agent continuity requires a verifiable link between the agent and its platform history.

---

### C8: Configuration Rollback with Identity Verification

**Scenario:**
A kernel update causes instability. The user wants to roll back to the previous kernel version. The system needs to verify that the rollback target is a legitimate prior state.

**With identity:**
The State Chain already records every software configuration. The system can verify that the rollback target is signed by its own identity and that the target state actually existed in the system's history.

**Without identity:**
The rollback is a filesystem operation (BTRFS snapshot restore, package manager downgrade). Identity is not involved.

**Identity required?** ❌ No. Configuration rollback is a standard package management and filesystem capability. Identity adds verification, but the basic operation does not require it.

---

### C9: Compliance and Audit History

**Scenario:**
A corporate device running Theseus must prove to an IT auditor that it has never been tampered with — that all hardware and software changes were authorized and recorded.

**With identity:**
The complete State Chain provides a verifiable audit trail of every configuration change, signed by the system's identity. The auditor can verify the chain and the signatures.

**Without identity:**
Audit relies on logs, which can be altered. Without cryptographic identity anchoring, there is no way to prove that an audit log belongs to this specific system and has not been tampered with.

**Identity required?** ✅ Yes. Cryptographic audit trails require identity anchoring.

---

### C10: Long-Term Digital Preservation

**Scenario:**
A user wants to preserve their digital environment for 20+ years. Over this period, every hardware component will be replaced multiple times. When the current system is finally retired, the user wants to verify that the final backup represents the complete history.

**With identity:**
The final State Chain, signed by the original Root Keypair, provides a complete, verifiable history of the system from genesis to retirement. Even if no hardware from the original system survives, the identity provides continuity.

**Without identity:**
The user has backups of data and configurations. There is no way to link these backups into a coherent system history. Each backup is a snapshot of "some hardware at some time."

**Identity required?** ✅ Yes. Long-term preservation requires a persistent anchor that outlives all physical components.

## 3. Capability Priority Matrix

| Capability | Identity Required | Utility Value | Complexity Cost | M1 Candidate |
|------------|------------------|---------------|-----------------|--------------|
| C1: Architecture-independent migration | ✅ Yes | High | High | No |
| C2: Storage replacement without reinstall | ✅ Yes | High | Medium | **Yes** |
| C4: Clone/fork detection | ✅ Yes | Medium | Medium | No |
| C5: Secure ownership transfer | ✅ Yes | Medium | Low | No |
| C6: Multi-device identity | ✅ Yes | Medium | High | No |
| C7: Autonomous agent continuity | ✅ Yes | High | High | No |
| C9: Compliance and audit | ✅ Yes | Medium | Medium | No |
| C10: Long-term preservation | ✅ Yes | High | Low | **Yes** |
| C3: Hot hardware replacement | ❌ No | High | Low | No identity needed |
| C8: Configuration rollback | ❌ No | High | Low | No identity needed |

**Key insight:** Only two M1 capabilities actually require identity:
1. **C2: Storage replacement without reinstallation** — the core M1 deliverable from R1
2. **C10: Long-term preservation** — the ultimate justification for the entire identity model

The other identity-enabled capabilities (C1, C4, C5, C6, C7, C9) are valuable but belong to later milestones.

## 4. Minimum Viable Identity for M1

M1 only requires identity for one scenario: **storage replacement without reinstallation**.

The minimum viable identity for this scenario is:

### Requirements

1. The system can generate a unique identity at first boot.
2. The system can store data on the storage device and cryptographically bind it to the identity.
3. When storage is replaced, the system can verify that the data was created by the same identity.
4. The State Chain captures at least one event: "storage replaced."

### What M1 Identity Does NOT Require

| Feature | Not needed because |
|---------|-------------------|
| Fork detection | M1 does not involve cloning |
| Divorce statements | No forks to resolve |
| Ownership transfer | Single user, no transfer |
| Multi-device trust | Single device |
| Agent continuity | No agents in M1 |
| Hot hardware replacement | Storage replacement is cold (reboot required) |

### Identity Storage for M1

For M1, the simplest viable approach is:

> The Root Keypair is generated at first boot and stored on the system partition. A **Key Recovery Seed** is displayed to the user during genesis (printed on screen, also written to a file). If storage is replaced, the user provides the Recovery Seed, and the system regenerates the keypair and verifies the data.

This avoids TPM dependency, secure element availability, or complex key management. It is not maximally secure — it is maximally simple while still demonstrating the identity concept.

## 5. The "Why Identity" Answer

The user asked for a concrete answer. Here it is:

> **Persistent identity exists in Theseus so that storage and hardware replacement is indistinguishable from continuity — not from first boot.**

Without identity:
- Replace storage → "new system, data available"
- Replace CPU → "new system, maybe boots"

With identity:
- Replace storage → "same system, new storage component"
- Replace CPU → "same system, new CPU component"
- Replace everything → "same system, evolved hardware"

The identity model transforms hardware replacement from a catastrophic event (data recovery, reconfiguration, trust re-establishment) into a routine event (configuration change recorded in the State Chain).

If this transformation is not valuable, the identity model is not worth the complexity. The R1 Architecture Reduction assumes this transformation IS the core value of Theseus. If that assumption is wrong, the project scope should be reduced further.

## 6. Open Questions

| # | Question | Implications |
|---|----------|-------------|
| Q1 | Is the identity model worth the complexity if C2 (storage replacement) can be solved with simpler tools? (e.g., a hardware inventory file + manual migration) | Either identity is justified or the project scope is too broad. |
| Q2 | Should M1 ship without any identity at all and add it in M2 when fork detection or migration becomes relevant? | Delaying identity reduces risk but contradicts the "identity first" architecture. |
| Q3 | Is a Recovery Seed user experience acceptable for M1, or does it introduce too much user friction? | If users lose the seed, the identity model fails in its first demonstration. |

---

## 7. Decision

The following decisions are proposed for acceptance:

1. **Identity is justified** because it transforms hardware replacement from catastrophic to routine. This is the core value of Theseus.
2. **M1 requires identity** for the storage replacement scenario (C2). Identity is not optional.
3. **Minimum viable identity** is: Root Keypair generated at first boot, stored on system partition, with Recovery Seed for migration. No fork detection, no ownership transfer, no multi-device.
4. **If identity cannot be justified**, the project scope should be reduced to a simple hardware abstraction layer without persistent identity — effectively dropping the "Ship of Theseus" as a first-class invariant and treating it as a backup/migration tool.
